# Build Porting Plan (P6)

Responsibility: groups the 159 deployed builds into classes of identical simulation code, orders the classes as a diff tree rooted at the baseline `4e837520e886` (v0.34.22), summarises every edge, and records the Node/V8 and hash-origin findings that bound the bit-exact goal. Machine-readable twin: `Crates/Engine/src/Builds/BuildClasses.toml`. Generators: `Tools/BuildClassify.py`, `Tools/BuildPlanGen.py`, `Tools/BuildPlanDoc.py` (prose in `Tools/BuildPlanProse.py`).

## Summary

- 91 equivalence classes for 159 builds (class hash = SHA-256 over the sorted `(path, blob)` pairs of the simulation-relevant core files). The baseline class C000 holds 5 builds (v0.34.19 to v0.34.22).
- Risk split: high 16, medium 23, low 51. Estimated total if every class were ported: about 46,020 Rust lines (added lines plus a quarter of deleted lines over all edges; code touched by several edges is counted repeatedly, so this is an upper bound).
- Eras by class: seedrandom `S` 44 classes (88 builds, 64% of weight), sfc32 without DetMath `F` 24 (36, 22%), sfc32 with DetMath `D` 23 (35, 14%). The baseline is era D, the only era that does not depend on the host `Math.*` (see Node/V8). Era-changing edges: C011->C013 (D->F), C035->C036 (F->S).
- Weights are estimated from `Index.csv` (2,088 sampled records, not the full public volume): each UTC day counts as 1, split among the builds in proportion to their Public samples of that day (all samples if none is Public). The sum over all classes is 406 day-equivalents. Real game counts per day are not in the index; multiply by the daily public game count for a game estimate.
- Hash origin: `turn.hash` in records is produced by the clients (browser workers), not by the server; the server stores the majority value. Until v0.34.25 the server never runs the engine; from v0.35.0 (PR #5807) it replays games in a subprocess only to settle disputed winner votes (no hashes are written there).
- V8 finding: every build's Dockerfile uses `node:24-slim` (V8 13.6), where `Math.pow` is already `std::pow` (platform libm) while exp/log/atan2/sin/cos are still fdlibm ports; V8 15.0 switches them all to LLVM libc. Because clients, not the server, produce the hashes, what matters is the players' browsers; see the Node/V8 section.

## Method

1. Core roots per commit: `src/core/` before the monorepo split (upstream e82286146, first seen in v0.35.0), and `packages/{engine,engine-lib,engine-api,shared}/src/` after it. The root prefix is stripped, so moved files keep their key (no key collisions in any build; asserted).
2. Excluded from the hash (wire/API schemas, client views, themes, asset or transport helpers, serialisation): `ApiSchemas`, `ClanApiSchemas`, `CosmeticSchemas`, `StatsSchemas`, `WireSchemas`, `WorkerSchemas`, `ZbinWire`, `LevelBadgeWire`, `AssetPaths`, `AssetUrls`, `Base64`, `CloseCodes`, `ClusterConfig`, `CustomFlag`, `EventBus`, `Format`, `PatternDecoder`, `ServerList`, `MapPlayerCounts`, `FetchGameMapLoader`, `GameMapLoader`, `game/GameView`, `game/ReadViews`, `game/NameBoxCalculator`, `game/UserSettings`, `game/SnapshotHeader`, `configuration/PastelTheme*`, `configuration/Colors`, `configuration/ColorAllocator`, `utilities/DebugSpan`, `worker/*`, `snapshot/*` (save/restore codec, reads state only). Everything else stays in, including `Schemas.ts` (zod defaults of the game config), `configuration/*Config.ts` (Dev/Prod overrides), `Maps.gen.ts`, name tables, `GameUpdates` and `validations/*`. When unsure a file is included, so classes may be split more finely than strictly necessary but are never merged wrongly.
3. Maps: `resources/maps/<map>/{map.bin,map4x.bin,map16x.bin,mini_map.bin,manifest.json}` are hashed per build for every map directory; map changes are reported per edge and do not split classes. Tournament maps (`tourney2teams`, `tourney3teams`, `tourney4teams`, `tourney8teams`) have no directory of their own (7 build/map pairs); they are resolved through the build's map loader and are not covered by the per-map hashes.
4. Tree: candidate edges are the 7 classes with the fewest differing files plus the temporal neighbours; the edge cost is the number of changed lines (`git diff --numstat` per differing blob, whole file counted for added/removed files). A minimum spanning tree rooted at the baseline (Prim) gives the parents. The ids C000.. are the porting order: from the root, the frontier node with the highest weight per changed line is taken next, so heavy classes near the baseline come first, then the tree is walked towards older and newer builds.
5. Edge summary: functions are the enclosing class/method of each hunk in the child file (heuristic); PRs are the `(#NNNN)` numbers in the subjects of the commits touching the core between the two representative commits (symmetric difference, so release-branch cherry-picks appear on both sides); the classification comes from the file path and a numeric-literal-only test. Size estimate = added lines + deleted lines / 4. Risk: high if a PRNG/DetMath file changed, a file is a rewrite, or more than 2,000 lines differ; medium for AI or pathfinding changes or more than 300 lines; low otherwise.

## Main risks

1. Pre-DetMath eras (S and F, 124 of 159 builds, 86% of the weight) call `Math.pow`/`Math.exp` in core formulas (for example troop growth `Math.pow(troops, 0.73)`, structure cost `Math.pow(2, n)` and the logistic curve in `Util.ts`). Their recorded hashes are the clients' majority and depend on the clients' JS engines (below); a bit-exact Rust port needs the right libm per build, which cannot be known without trial against the records. Mitigation: replay the sampled records of those builds with Node 22 (legacy fdlibm pow) and Node 24 (`std::pow`) in the reference tracer and keep the variant that matches; expect some builds to be unreproducible if the majority engines disagreed.
2. The seedrandom-to-sfc32 switch needs an ARC4/seedrandom port for era S (88 builds, 64% of the weight). Edges touching `PseudoRandom.ts` or `DetMath.ts`: C013, C036, C040, C079, C081; `PseudoRandom.ts` also changes on release-branch edges without changing era, so diff those edges for seed or warm-up changes before assuming the algorithm is the same.
3. Sampled records are few for most classes (many builds have 3 records), so a class can be ported and still fail on a rarely exercised branch. Port in the order given and keep every class's records as regression tests.
4. Maps change often: 263 `map.bin` variants over 151 maps (78 maps changed at least once), 739 `manifest.json` variants. Replays must load the map files of the record's own build (stored by content hash), not the baseline's. The oldest builds also ship `mini_map.bin` instead of `map4x.bin`/`map16x.bin` (28 maps). Not every map variant is used by a record.
5. Release branches: many builds are not on main (Builds.md), so the tree mixes main-line and branch commits and the PR list of an edge can include PRs that belong to the other side of the edge. Selecting the engine by `gitCommit` (class table in `BuildClasses.toml`) is exact; any date-based selection is not.
6. Schema-only edits are included in the hash by design (see Method 2), so some small classes differ from their parent only by config-schema or name-table changes; these are cheap but cannot be merged without checking.

## Node / V8 and the origin of the hashes

### Who computes `turn.hash`

- `GameImpl.hash()` runs inside the engine in every client's worker. Clients send `{type:"hash", turnNumber, hash}` messages; `GameServer` keeps them per client (`client.hashes`), `DesyncDetector.findOutOfSyncClients` takes the most common value, and `GameServer` writes `this.turns[turn].hash = mostCommonHash` (baseline `src/server/GameServer.ts:1999`; v0.25.20 `GameServer.ts:712`). Clients that disagree are flagged as desynced.
- Checked builds (v0.25.20, v0.34.22): the server code never imports `GameRunner` or calls `executeNextTick`. From v0.35.0 (PR #5807, 2026-10-06; ancestor of every build from `dfd420fd7836` on, not of v0.34.x) `GameServer` runs `replayWinnerInChild` (`packages/engine/src/WinnerReplay.ts`, one subprocess) to settle disputed winner votes; it reports winner and stats only. Singleplayer records carry the hash of the single local client.
- Consequence: the Node version in the server Dockerfile does not influence the recorded hashes. What matters is the JS engine of the majority of the players: mostly Chrome-family V8 (Chrome milestone N ships V8 N/10, for example Chrome 141 = V8 14.1), plus Firefox (SpiderMonkey) and Safari (JavaScriptCore), whose libm differs again. A recorded majority on pre-DetMath builds means most clients agreed bit for bit on every sampled turn; upstream still added DetMath (PR #5191, first build v0.34.0) because last-bit differences between engines are real desyncs (the DetMath header comment says so).

### Node per build

All 159 builds have `FROM node:24-slim` in the Dockerfile (a floating tag, so the minor version is whatever Docker Hub served at image build time; no `.nvmrc` exists in any build). `package.json` `engines` (`node >=24.15.0 <25`, `npm >=12.1.0 <13`) appears only in the 20 newest builds. The Node major is therefore 24 for the whole period.

| Node / V8 | `Math.pow` | `exp` `log` `atan2` | `sin` `cos` |
|---|---|---|---|
| Node 20.x = V8 11.3 | fdlibm port (`ieee754::legacy::pow`) | fdlibm port | fdlibm port |
| Node 22.x = V8 12.4 (local reference) | fdlibm port | fdlibm port | fdlibm port |
| Node 24.x = V8 13.6 (all builds' Dockerfile) | **`std::pow` (platform libm)**; flag `use_std_math_pow` defaults to true since V8 13.3 (not AIX); `x**2` and `x**0.5` special-cased | fdlibm port | fdlibm port (`V8_USE_LIBM_TRIG_FUNCTIONS` not found in Node's v8 gyp files; V8's GN build has `v8_use_libm_trig_functions` for glibc-derived sin/cos in Chrome) |
| Node 25.x = V8 14.1 | `std::pow` | fdlibm port | fdlibm port |
| V8 14.6 to 14.9 | `std::pow` | fdlibm port (six functions unchanged; other functions trimmed) | fdlibm port |
| V8 15.0 and later | LLVM libc `pow` | LLVM libc | LLVM libc |

Sources: `src/base/ieee754.cc`, `src/numbers/ieee754.cc` and `src/flags/flag-definitions.h` at V8 11.3.244.8, 12.4.254.21, 13.0 to 13.6 (lkgr branches and 13.6.233.10), 14.1 to 14.9 and 15.0 lkgr, 15.2, 15.5, 15.9 and `main` (V8 16.0), plus Node `deps/v8/include/v8-version.h` on v20.x to v25.x. The V8 `ieee754.cc` is 3,036 lines up to 14.5, 2,969 lines at 14.8 and 14.9, 382 lines at 15.0 (wrapping `LIBC_NAMESPACE::shared::{acos,asin,atan,atan2,cbrt,cos,exp,expm1,log,log10,log1p,log2,pow,sin,tan}` from `third_party/llvm-libc`) and 245 lines on main. The exact commit of the switch was not bisected (it lies between the 14.9 and 15.0 branches); the Chrome stable date for 15.0 (Chrome 150) was not verified here; with a 4-week cadence from Chrome 144 (January 2026) it would be about mid 2026, which fits DetMath arriving on 2026-08-30.

Implications for the V8 fdlibm port:

- The six fdlibm routines (`exp`, `log`, `atan2`, `sin`, `cos`, `pow`) exist unchanged in V8 up to 14.9, so one port of `ieee754.cc` (V8 12.4 or 13.6) covers all fdlibm behaviour; `pow` is `legacy::pow` there.
- `Math.pow` is the outlier: from V8 13.3 it is the platform `std::pow` (glibc on Linux, UCRT on Windows, Apple libm on macOS; none is fdlibm). Clients on Chrome 133 or later (February 2025, i.e. the whole period) therefore produced pow results from whatever libm they ran on; clients on older V8 used legacy fdlibm pow. The port should make the pow implementation a per-build choice (`fdlibm`, a correctly rounded glibc-style `pow`, or LLVM libc) selected by the trial against records described above.
- From V8 15.0 (Chrome 150, likely mid 2026 onward) clients use LLVM libc for all six functions (correctly rounded in almost all cases, differing from fdlibm in the last bit now and then). Era F builds seen on or after 2026-07-01 are the most exposed: classes C013, C014, C015, C016, C017, C018, C019, C020, C021, C022, C023, C024, C025, C026, C027, C028, C029, C080.
- Local reference note: the baseline worktree runs Node 22 (V8 12.4, legacy fdlibm pow) although production used Node 24 and, more to the point, players' browsers. This does not matter for era D (no host transcendental calls); for eras S and F run the reference under Node 22 and 24 and compare with the record hashes.

## Map-file changes

Per-class map changes are in the last column of the class table and in `maps_changed` of `BuildClasses.toml` (`<map>:<file>`). Totals over the 159 builds (distinct content hashes per map and file): `map.bin` 263 variants / 151 maps (78 maps changed), `map4x.bin` 333 / 151 (96), `map16x.bin` 329 / 151 (94), `manifest.json` 739 / 151 (139). A changed `map.bin` changes terrain and must be loaded for replays of that build; many `manifest.json`-only changes are metadata. Plan: store map files by content hash and let `BuildClasses.toml` plus a per-build map index select them.
